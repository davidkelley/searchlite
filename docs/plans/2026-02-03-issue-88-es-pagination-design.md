# Issue 88 ES-Style Pagination and MGET Design

## Architecture
The codebase already implements the core behavior for issue 88 in `searchlite-core` and `searchlite-http`. The reader accepts `from` and `search_after` on `SearchRequest`, returns `Hit.sort_key` and `SearchResult.next_search_after`, and enforces a fixed page cap (`MAX_PAGE_SIZE = 1000`). HTTP exposes `POST /indexes/{name}/mget` and `POST /indexes/{name}/multi_search`, and extends `/search` to validate pagination combinations. The architecture for closing this issue focuses on verification and public contract alignment rather than new core logic. The goal is to confirm the existing implementation matches the issue requirements and then document the supported behavior in the OpenAPI spec, JSON schema, and docs. We should keep the current pagination precedence (reject mixed cursor/from/search_after) unless we decide to relax it, because the explicit 400s are already implemented in both core and HTTP. The `search_after` token format is a JSON array of sort values plus doc id and segment ordinal, which provides deterministic ordering across segments but is only valid until the index commits a new generation or compaction changes segment ords. That stability window should be documented so clients understand the constraints. For multi-search, the design is to allow sequential or parallel execution with bounded concurrency while preserving result order; the API already supports this and just needs specification. For mget, the reader resolves live docs via a doc-id lookup map, preserves request order, handles duplicates, and optionally returns stored docs.

## Components and Data Flow
HTTP `/search` parses the request body into `SearchRequest`, validates pagination rules and page caps, applies vector candidate defaults, and then invokes `reader.search` in a blocking task. The reader builds a `SortPlan`, decodes cursor or `search_after` state if present, and executes top-k collection. It skips the requested `from` offset after ranking, materializes hits, and, when paging, sets either `next_cursor` or `next_search_after`. Each hit includes an optional `sort_key` JSON array, which mirrors the `search_after` token encoding and lets clients resume precisely. For `/mget`, HTTP validates ids and caps, then calls `reader.mget`, which uses `doc_lookup` to find live documents, avoids deleted docs, and produces a `Vec<MgetDoc>` preserving input order and duplicates. For `/multi_search`, HTTP validates each request with the same pagination rules as `/search`, then executes either sequentially or in parallel using a semaphore, returning `MultiSearchResponse` in the original order. The core multi-search path is a simple loop over `reader.search` calls and is expected to share the reader instance for efficiency.

## Error Handling, Limits, and Testing
Pagination invariants are enforced consistently in core and HTTP: limit 0 disallows cursor, `from`, `search_after`, and explain; cursor cannot be combined with `search_after` or non-zero `from`; `search_after` cannot be combined with non-zero `from`. Page caps are enforced when returning hits, using `from + size <= MAX_PAGE_SIZE`. Mget is capped at `MAX_MGET_IDS = 1024` and validates ids before attempting to fetch. These rules should be documented in `openapi.yaml` and `search-request.schema.json` so clients know why they may receive 400s. Tests already exist for mget ordering and missing docs, search_after round-trip, and multi-search HTTP behavior. The remaining work is to verify those tests are still present and passing, and to add or update documentation to mention the new endpoints and pagination behavior. If any gaps are found, add small targeted tests (HTTP or reader) to cover them. The documentation should also note the stability window for `search_after` tokens (valid until the next commit/refresh that changes segment ords) and clarify that `size` is an alias for `limit` in JSON requests.
