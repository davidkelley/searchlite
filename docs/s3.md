# S3-Compatible Storage

By default, Searchlite reads and writes its index on local disk. The
`searchlite-s3` crate lets readers open an index that lives in S3, R2, MinIO,
or any other S3-compatible object store -- same API, same queries, no local
writes required on the reader side.

> **Status:** Experimental. The API is functional but may change before 1.0.

---

## Why it exists

Searchlite's writer wants exclusive access to a single index directory: one
WAL, one manifest, atomic commits. That's a great fit for a single-tenant
service running on one box, and a poor fit when you want many read replicas
of the same index running on different machines.

S3-compatible storage solves the read-side fan-out. Bake the index once on
any machine that can write to disk, sync it to a bucket, and any number of
read-only processes can `open_index_read_only` against the same prefix.
Readers stay completely stateless -- no local cache to warm up, no
disk to provision, no replication coordinator. Writes stay where they
already work: against a local index that you control end-to-end.

The shape works equally well for short-lived workloads (Lambda, Cloud Run,
Fly Machines) and long-running services (Kubernetes, ECS) -- anywhere you'd
rather scale by spinning up another stateless reader than by reshaping the
write path.

---

## When to use it

| Scenario | Use S3 storage? |
|---|---|
| **Many read replicas of the same index** | Yes -- bake once, every replica opens read-only |
| **Edge / serverless readers** | Yes -- no local disk to provision; cold open fetches the manifest plus per-segment artifacts |
| **Blue/green index swaps** | Yes -- publish a new prefix, flip readers, drop the old one |
| **Tenant-per-prefix multi-tenancy** | Yes -- each tenant gets a prefix, readers pick prefix per request |
| **Single-writer + warm standby** | Sometimes -- the standby opens read-only from S3 while the primary writes locally |
| **Active read-write from S3** | No -- writes still go through a local mutable index |
| **Browsers / WASM** | No -- WASM uses IndexedDB; see [wasm.md](wasm.md) |

If a single process is doing both writes and reads, stay on a local index.
S3 storage shines when the read side fans out beyond what one writer can
serve.

---

## The bake-and-sync workflow

Three steps, three places state lives:

```
   ┌─────────────────────┐         ┌─────────────────────┐
   │  Writer process     │         │  S3 / R2 / MinIO    │
   │  ───────────────    │         │  ───────────────    │
   │  Index::create      │         │  bucket/prefix/     │
   │  writer.commit()    │         │   ├── MANIFEST.json │
   │  index.compact()    │  ───►   │   ├── seg_*.terms   │
   │                     │  sync   │   ├── seg_*.post    │
   │  bake locally       │         │   ├── seg_*.fast    │
   └─────────────────────┘         │   ├── seg_*.docs    │
                                   │   └── seg_*.meta    │
                                   └──────────┬──────────┘
                                              │
                                              │ open_index_read_only
                                              │
              ┌──────────────────┬────────────┴────────────┬──────────────────┐
              ▼                  ▼                         ▼                  ▼
     ┌────────────────┐  ┌────────────────┐       ┌────────────────┐  ┌────────────────┐
     │ Reader 1       │  │ Reader 2       │  ...  │ Reader N       │  │ Reader N+1     │
     │ (stateless)    │  │ (stateless)    │       │ (stateless)    │  │ (stateless)    │
     └────────────────┘  └────────────────┘       └────────────────┘  └────────────────┘
```

1. **Bake locally.** Run a normal mutable `Index` on a machine with writable
   disk. Add documents, commit, optionally `compact()` to reduce segment
   sprawl. The local directory ends up holding the same files any
   filesystem-backed index would: one `MANIFEST.json` and a handful of
   per-segment artifacts (`*.terms`, `*.post`, `*.docs`, `*.fast`, `*.meta`).
2. **Sync to S3.** Call `sync_to_s3(local_root, s3_config)`. The helper
   walks the directory, uploads every segment artifact first, and
   publishes `MANIFEST.json` **last** as the visibility fence. Until the
   manifest lands, the prefix looks empty to readers; once it lands,
   every artifact it references is already in place.
3. **Open read-only from any reader.** `open_index_read_only(s3_config)`
   returns a real `searchlite_core::Index` whose mutators are all wired
   off. Search, mget, and aggregations work exactly like a filesystem
   index. The reader caches segment data in RAM (default 64 MiB
   byte-weighted LRU) so hot terms don't go back to S3 on every query.

The publish ordering means a sync that fails midway leaves no remote
manifest at all -- readers see "index not found" rather than a dangling
manifest pointing at half-uploaded segments.

## Quickstart

Add the crate to your `Cargo.toml`:

```toml
[dependencies]
searchlite-core = "0.8"
searchlite-s3 = "0.2"
tokio = { version = "1", features = ["full"] }
serde_json = "1"
```

`searchlite-s3` brings `aws-sdk-s3` and the `tokio-runtime` feature on
`searchlite-core` along with it -- you don't need to enable either
manually. `serde_json` is used by the document-construction snippet
below.

### Bake an index locally

This is identical to any other filesystem-backed Searchlite index:

```rust
use searchlite_core::api::{
    builder::IndexBuilder,
    types::{Document, IndexOptions, Schema},
};
use std::path::PathBuf;

let local_root = PathBuf::from("/tmp/products");
let schema = Schema::default_text_body();
let opts = IndexOptions {
    path: local_root.clone(),
    create_if_missing: true,
    ..Default::default()
};

let index = IndexBuilder::create(&local_root, schema, opts)?;
let mut writer = index.writer()?;
writer.add_document(&Document {
    fields: [
        ("_id".into(), serde_json::json!("doc-1")),
        ("body".into(), serde_json::json!("Searchlite is a fast embedded search engine.")),
    ].into_iter().collect(),
})?;
writer.commit()?;
// Optional: collapse the segment list before publishing.
index.compact()?;
drop(index);
```

### Sync to S3

```rust
use searchlite_s3::{sync_to_s3, S3Config, S3Credentials};

let s3_config = S3Config {
    region: "us-east-1".into(),
    bucket: "my-search-indexes".into(),
    prefix: Some("products/v1".into()),
    credentials: S3Credentials::LoadFromEnv,
    ..S3Config::aws_default()
};

let report = sync_to_s3(&local_root, s3_config).await?;
println!("Uploaded {} files / {} bytes", report.files, report.bytes);
```

`SyncReport` carries the file and byte counts so you can assert against them
in CI or log them for capacity planning.

### Open read-only from any reader

```rust
use searchlite_core::api::types::SearchRequest;
use searchlite_s3::open_index_read_only;

let s3_config = S3Config {
    region: "us-east-1".into(),
    bucket: "my-search-indexes".into(),
    prefix: Some("products/v1".into()),
    credentials: S3Credentials::LoadFromEnv,
    ..S3Config::aws_default()
};

let index = open_index_read_only(s3_config).await?;
let reader = index.reader()?;
let results = reader.search(&SearchRequest::new("search engine").with_limit(5))?;
for hit in &results.hits {
    println!("{} (score: {:.2})", hit.doc_id, hit.score);
}
```

The returned `Index` is a regular `searchlite_core::Index` -- everything in
the [Rust API guide](rust-api.md) that doesn't mutate the index works
unchanged.

## Provider compatibility

`searchlite-s3` targets three S3-compatible backends. Each gets its own
`S3Config` defaults:

| Provider | `endpoint_url` | `region` | `force_path_style` | `conditional_put` |
|---|---|---|---|---|
| **AWS S3** | `None` | actual region | `false` | `true` |
| **Cloudflare R2** | `https://<account>.r2.cloudflarestorage.com` | `auto` | `false` | `false` (opt in once verified) |
| **MinIO / LocalStack** | your endpoint URL | any (e.g. `us-east-1`) | `true` | `true` |

`S3Config::aws_default()` and `S3Config::r2_default()` provide the boilerplate;
you fill in `bucket`, `credentials`, and -- for R2 -- the `endpoint_url`.

### Authentication

Two credential sources, picked via `S3Credentials`:

```rust
// Inside AWS (EC2, ECS, EKS, Lambda) -- use the default chain:
//   env vars → shared credentials file → IMDS / instance role.
S3Credentials::LoadFromEnv

// Outside AWS (R2, MinIO, dev laptops) -- pass the keys explicitly:
S3Credentials::Static {
    access_key_id: "...".into(),
    secret_access_key: "...".into(),
    session_token: None, // Some(...) for STS / scoped R2 tokens
}
```

Use `LoadFromEnv` for AWS-hosted readers so credentials rotate automatically.
Use `Static` for everything else -- R2 account-scoped tokens, MinIO root
keys, LocalStack throwaway credentials.

### Conditional PUTs

Cloudflare R2 added atomic conditional PUTs (`If-Match` / `If-None-Match`) in
late 2024. Stage 10b's `S3Config::conditional_put` defaults to `false` for
R2: the helper refuses to issue a conditional PUT against a backend whose
flag is `false` rather than silently sending headers an older R2 endpoint
would ignore. Flip the flag once you've confirmed your account/bucket
supports it.

AWS S3 and MinIO support conditional PUTs unconditionally; the
`aws_default()` profile leaves the flag on.

## Key shape and prefixes

`sync_to_s3` walks the local index directory and uploads every regular file
verbatim. Relative paths (relative to `local_root`) become BlobStore keys.
The `S3Config::prefix`, if set, is prepended **once** inside `S3BlobStore`
-- the manifest and the walker never see it.

For an index laid out like this on disk:

```
/tmp/products/
├── MANIFEST.json
├── seg_a.terms
├── seg_a.post
├── seg_a.fast
├── seg_a.docs
└── seg_a.meta
```

with `prefix: Some("products/v1".into())`, the bucket ends up holding:

```
products/v1/MANIFEST.json
products/v1/seg_a.terms
products/v1/seg_a.post
...
```

The `prefix` itself is validated the same way segment keys are:
relative, non-empty after trim, no `..`, no backslashes, no platform
prefix. Leading/trailing slashes are not part of the prefix -- the helper
joins with `{prefix}/{key}` itself.

### What the syncer skips

`sync_to_s3` is fail-closed. The preflight refuses to run if it finds:

- `MANIFEST.json.pending` (a half-finished commit that needs reconciliation)
- a non-empty `wal.log` (uncommitted writes that the read-only path won't
  replay)
- any `*.tmp-*` staging file (atomic-write artifacts left from a crash)
- a missing, malformed, or pre-Stage-9a manifest (legacy v1 manifests with
  absolute segment paths can't be safely transplanted)

In every case the fix is the same: reopen the source index mutably to let
its commit-time reconciler finish, then re-run `sync_to_s3`.

The walker itself also skips dot-files, `wal.log`, and the top-level
`MANIFEST.json` (which is uploaded last, separately). The same predicate
runs over every key the manifest references, so a manifest that names a
file the walker would skip is rejected up front rather than producing a
remote index that points at a key that was never PUT.

## Read-only enforcement

`open_index_read_only` sets `IndexOptions.read_only = true` unconditionally
and threads that flag through every mutator entry point on `Index`:

- `Index::writer()` -- errors with "index is read-only"
- `Index::compact()` -- errors with "index is read-only"
- `Index::merge_segments()` -- errors with "index is read-only"

That's the same enforcement any local index gets from setting `read_only`
manually; S3-backed indexes just have it pinned on. If you need to mutate,
re-bake locally and re-sync rather than trying to write through the
adapter.

A consequence: pending-manifest recovery is also fail-closed on the read
side. If a remote prefix somehow ends up with a `MANIFEST.json.pending`
artifact, the open path won't try to promote it -- reopen the source
index mutably to reconcile, then re-sync to publish a clean manifest.

## Feature gates and platform support

| Crate | Feature | Notes |
|---|---|---|
| `searchlite-core` | `tokio-runtime` | Enables the sync→async bridge that drives `aws-sdk-s3` futures from non-async callers. `searchlite-s3` enables this transitively; you don't need to set it manually unless you're calling the runtime bridge directly. |
| `searchlite-s3` | (none) | The crate has no Cargo features. It ships with `aws-sdk-s3 = 1` baked in. |

`searchlite-s3` is `#![cfg(not(target_arch = "wasm32"))]` -- `aws-sdk-s3`
depends on the Tokio reactor and native TLS, neither of which compile to
WASM. WASM consumers stay on the in-browser IndexedDB path described in
[wasm.md](wasm.md).

If you're driving `sync_to_s3` or `open_index_read_only` from sync code,
wrap them in a `tokio::runtime::Runtime`:

```rust
let rt = tokio::runtime::Runtime::new()?;
let index = rt.block_on(open_index_read_only(s3_config))?;
```

If your binary already has `#[tokio::main]`, you can `await` them
directly. The bridge is safe to call from inside an active Tokio runtime
of either flavor: multi-thread runtimes use `block_in_place` to park the
worker, and current-thread runtimes route the future to a
`std::thread::scope`-spawned worker on a global multi-thread bridge
runtime. See [`searchlite_core::runtime`](../searchlite-core/src/runtime.rs)
for the full contract.

## What's the same

Everything on the read path. S3-backed indexes support the full feature
set:

- All query types (bool, phrase, fuzzy, prefix, wildcard, function scores,
  regex, etc.)
- Filters, aggregations, highlighting, collapsing
- Multi-search and mget
- Vector search (with the `vectors` feature flag on `searchlite-core`)
- Cursor-based and `search_after` pagination
- Stage 9b SHA-256 segment integrity verification under the default
  `Strict` checksum policy

Search results are bit-for-bit identical for the same data and queries
regardless of storage backend.

## What's different

| | Filesystem | S3-backed (read-only) |
|---|---|---|
| **Writer access** | One process at a time, in place | Bake locally → sync → readers open read-only |
| **Mutators on the read side** | Available | All disabled (`writer`, `compact`, `merge_segments`) |
| **Cold read latency** | OS page cache miss → disk I/O | Cache miss → S3 GET (single-flight inside `CachedBlobStore`) |
| **Hot read latency** | Page cache hit | RAM cache hit (default 64 MiB byte-weighted LRU) |
| **Replication** | Filesystem snapshot / rsync | Implicit -- one bucket, many readers |
| **Capacity** | Local disk | Effectively unlimited |
| **Visibility fence** | Atomic manifest rename | `MANIFEST.json` uploaded last as the publish fence |

Steady-state S3 latency depends on which reads stay in the RAM cache.
Bounded postings and docstore range reads single-flight through
`CachedBlobStore`, so hot terms and recently-fetched documents avoid
the network. Whole-file segment artifacts (terms, fast fields, segment
meta, plus vectors under the feature) are read at open and -- under the
default `Strict` checksum policy -- re-verified on every fresh
`Index::reader()`, which means each new reader pays one whole-object
read per segment artifact. Long-lived readers amortise that cost
across many queries; switching to `ChecksumPolicy::TrustManifest` lets
each new reader skip whole-file verification entirely if you trust the
bucket.

## Limits and caveats

- **No cross-process write coordination.** `sync_to_s3` doesn't take any
  remote lock; if two writers race to publish to the same prefix, the
  visibility fence (manifest-last) keeps each individual sync coherent,
  but the final state is whichever writer published its manifest second.
  Use distinct prefixes per writer or coordinate publishes externally if
  multiple writers can target the same bucket.
- **Eventual consistency on some endpoints.** AWS S3 is strongly
  consistent for new-key reads since 2020. R2 and MinIO are likewise
  strongly consistent. LocalStack and older S3-clones may not be -- if
  yours isn't, expect a brief window after `sync_to_s3` returns where
  some readers still see the previous manifest.
- **No partial-publish reuse.** A failed sync that uploaded half the
  segments leaves orphaned objects under the prefix. Re-running
  `sync_to_s3` re-uploads everything verbatim; nothing diffs against
  what's already in the bucket. For large indexes that publish often,
  consider a versioned-prefix scheme (`prefix/v1`, `prefix/v2`) so a
  failed sync to `v2` doesn't pollute the live `v1`.
- **macOS keychain TLS init flake.** On macOS, the AWS SDK's native-TLS
  init occasionally races against the keychain on the first call per
  process. `S3BlobStore::new` serializes init within a process via a
  `Mutex`, but cross-process this can still surface as a one-shot
  `TrustStore configured to enable native roots but no valid root
  certificates parsed!` panic. Fresh re-runs always succeed; long-lived
  processes are unaffected after the first successful init.
